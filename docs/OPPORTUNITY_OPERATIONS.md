# GFC 창업 기회 수집·발행 운영 방법

이 문서는 2026-09-15 작성한 기능의 사용법이다. 코드 구현·로컬 검증과 운영 적용은 다르다. 이 변경의 운영 적용 상태와 실제 출처 표본은 `OPPORTUNITY_VALIDATION.md`를 확인한다.

## 학회장과 회원에게 보이는 출력

| 화면 | 용도 | 사용자 |
|---|---|---|
| `/notice` | 기존 운영진 공지와 주간 StartupRadar 공지 | 기존 공개/회원 권한 유지 |
| `/opportunities` | 공식 모집을 확인한 전체 기회. 매일 수집 후 주간 발행 전에도 열람 | GFC 회원·관리자 |
| `/opportunities/rolling` | 상시 접수. 매주 신규 소식처럼 반복하지 않음 | GFC 회원·관리자 |
| `/opportunities/<공고 번호>` | 대상·마감·조건·공식/신청 링크·마지막 확인·정보 부족·근거 | GFC 회원·관리자 |
| `/opportunities/submit` | 공식 링크 제보와 처리 현황 | 회원은 제보만, 관리자는 검토 가능 |
| `/opportunities/admin` | 기관·채널, 매일 수집 시각, 장애·부분 수집, 검토함, 긴급 후보 | 관리자 |
| `/opportunities/review/<공고 번호>` | 내용 정정, 게시 제외, 원문·정정 이력 | 관리자 |
| `/radar/weekly-admin` | 주간 발행 요일·시각과 이미 발행한 공지 정정 | 기존 관리자 기능과 통합 |

프로그램 분류는 공공지원, 경진대회, 배치·액셀러레이팅, 기업 협업, 교육·공간, 행사·네트워킹, 투자 검토 접수다. 기관 유형은 별도다. 재단이 배치를 운영한다고 VC로 표시하지 않는다. 모집 상태·단계·지역·마감일로 검색할 수 있다. 대상·지역·날짜 미확인 공고는 해당 조건 검색에서 빠질 수 있다. 개인별 고급 프로필을 작성하지 않아도 기본 목록을 읽을 수 있다.

Telegram에는 주간 공지 제목, 신규·변경 수, 주요 예시와 웹 공지 링크를 보낸다. 웹 전체 내용을 여러 메시지로 나눠 보내지 않는다. 관리자의 발송 허용, 기존 구독 설정과 채널 상태가 모두 유효해야 한다. 같은 방이 여러 팀에 연결되어도 같은 주간 공지는 한 번만 처리한다.

## 매주 발행하는 요일·시간 바꾸기

1. 관리자 계정으로 로그인한다.
2. 공지 화면에서 **발행 일정·공지 정정**으로 들어간다.
3. 발행 요일과 시간을 선택하고 저장한다. 모두 한국 시간(Asia/Seoul)이다.
4. 매일 수집 시각은 **수집·검토 관리 → 매일 수집**에서 별도로 설정한다. 초기값은 오전 6시, 자동 수집은 비활성이다.

서버는 GitHub Actions에서 15분 간격으로 예약을 확인한다. 서비스 지연·실패 때문에 지정 시각과 실제 시각이 다를 수 있다. 이미 그 주에 자동 발행을 시도했다면 요일을 바꿔도 같은 주에 자동 재시도하지 않는다. 실패를 복구한 뒤 운영 담당자가 수동 실행한다. 실행 중인 작업을 시간만 보고 강제로 인계하지 않는다.

첫 매일 수집을 활성화·실행하기 전에는 기존 공공 API 주간 경로를 유지한다. 이후에는 저장된 매일 수집 결과로 주간 공지를 만든다. 최근 수집이 36시간을 넘으면 오래된 자료로 새 공지를 만들지 않는다. 일부 출처 실패는 표시하고 정상 자료는 유지한다. 전체 실패를 ‘이번 주 신규 공고 없음’으로 표시하지 않는다.

## 내용을 정정하거나 게시에서 빼기

1. 공고 상세에서 **이 공고 검토·정정**, 또는 관리자의 검토함에서 공고를 연다.
2. 사업명·분류·참여 방식·대상·지원 내용·주요 조건·신청 마감을 수정한다. 확인하지 않은 날짜·조건은 입력하지 않는다.
3. 정정 사유를 입력한다. 불필요하거나 모집과 무관한 공고는 **게시 포함**을 해제한다.
4. 저장한다. 원문·버전과 이전 내용, 사유는 남는다. 재수집이 관리자의 정정을 덮어쓰지 않는다.

원문에서 같은 항목이 바뀌면 ‘정정 충돌’로 표시한다. 공식 원문과 현재 정정을 비교한 뒤 다시 저장하면 충돌을 해제한다. 동시에 다른 사람이 수정했다는 안내가 나오면 작성 내용을 복사해 두고 새로 불러온 뒤 다시 검토한다. 상세 정정 화면의 **원문·정정 이력**에서 최근 30개를 읽을 수 있으며 전체 이력은 DB에 유지한다.

전체 모집 공고와 이미 발행된 주간 공지는 각각의 시점에 저장된 내용이다. 전체 목록을 고쳤다면 이미 발행된 주간 공지도 **발행 일정·공지 정정**에서 별도로 수정한다. 주간 공지 정정은 웹에 반영되며 이미 보낸 Telegram 메시지를 자동 수정·재전송하지 않는다. 아직 발송되지 않은 대기 메시지는 최신 공지 내용을 사용한다. 발송 중인 공지는 충돌 방지를 위해 정정을 잠시 제한한다. 발송 결과가 불확실한 건은 자동 재전송하지 않는다.

## 기관을 추가하거나 장애를 확인하기

기관 하나에 여러 채널을 둘 수 있다. ‘후보 기관’과 ‘연결 완료’는 다르다. 홈페이지가 열리는 것과 실제 모집 본문 수집이 되는 것도 다르다.

| 표시 | 의미와 조치 |
|---|---|
| 설정 필요 | 신규 요청, 선택자·렌더링·인증 설정 필요. 정상 연결로 집계하지 않음 |
| 연결 완료 | 설정 범위 안의 수집 성공. 범위 밖 공고까지 모두 수집했다는 뜻은 아님 |
| 접근 제한 | robots·차단·이용 정책 문제. 로그인·CAPTCHA·차단 우회 금지 |
| 일시 오류 | 네트워크 등 오류. 원인과 최근 시도·성공 시각 확인 |
| 부분 수집 | 일부 자료 저장, 일부 실패 또는 페이지 상한 도달. 저장분 유지 |

기존 기관은 **채널 추가·연결 요청**에서 주소와 방식을 입력한다. 지원 형식은 일반 게시판, 고정 페이지, RSS와 서버에 준비된 선택적 브라우저 읽기다. 선택자와 페이지 수는 개발 담당자가 검토한 값을 사용한다. 새 기관은 **목록에 없는 기관 연결 요청**으로 등록한다. 새 도메인은 검증 전 활성화되지 않는다. 새 브라우저 형식·뉴스레터는 연결 요청으로 남기고 개발 담당자가 확인한다. 공공 API 인증값은 서버 운영자가 관리하며 웹에 입력하거나 표시하지 않는다.

뉴스레터는 현재 미연결이다. 공식 발신자와 명시적으로 허가한 전용 수신함이 있어야 한다. 개인 메일 전체를 읽거나 임의 구독하지 않는다. 검색 제공자도 미연결이며 검색·뉴스레터 결과는 제보 검토함의 후보일 뿐이다. 제보는 `검토 중 → 반영 / 중복 / 제외 / 연결 확인 필요` 상태를 갖는다. 연결된 공식 채널과 일치하면 다음 수집에서 원문을 독립적으로 확인한다. 새 사이트는 연결 검토부터 진행한다.

## 읽을 때 주의할 정보 구분

- 참가팀 모집, 행사 참관, 투자 검토 접수를 구분한다. 디데이 발표팀과 참관 신청도 다르다.
- 무상 지원금, 상금, 선발 시 투자, 투자 검토 기회를 구분한다. ‘투자 연계’는 투자 확정이 아니다.
- 행사일·프로그램 기간을 모집 마감일로 사용하지 않는다. 월·일만 있고 적용 연도 근거가 없으면 미확인으로 둔다.
- 고정 URL의 기수가 바뀌면 별도 모집으로 저장한다. 다른 기수·지역·참가 방식은 중복으로 합치지 않는다.
- 소개 페이지나 뉴스레터 구독 링크만으로 ‘모집 중’이라고 표시하지 않는다.
- 주최자가 공식 페이지에서 연결한 외부 신청 폼은 근거가 될 수 있지만, 그 도메인을 자동 수집 허용 목록에 추가하지 않는다.
- 원문 확인은 신청 자격·선발 가능성 보증이 아니다. 실제 신청 직전에 공식 조건을 확인한다.

## 긴급 후보와 지표

다음 주간 발행 전에 마감되는 최근 신규 공고를 관리자에게 후보로 표시한다. 긴급 Telegram 발송은 구현·활성화하지 않았고 DB에서도 꺼짐을 강제한다. 별도 발송 정책·명시적 운영 설정을 구현하기 전에는 보낼 수 없다.

후보 기관 수, 실제 연결 기관 수, 최근 36시간 정상 기관 수, 하루 신규·변경 수, 실패·부분 수집·검토 대기 수, 날짜·신청 링크 확인 분자/분모, 유형별 저장 건수를 구분한다. 공식 게시 시각이 없으면 발견 지연은 ‘미측정’이다. 유형별 미연결 출처와 표본 누락은 검증 문서를 함께 본다. 후보 25개, 연결 몇 개라는 수치는 전국 포괄률이 아니다.

## 개발·서버 담당자: 적용 순서와 복구

기존 주간 발행 설정 변경의 PR 위에 확장했다. 기존 브랜치와 공지·발송 이력을 지우지 않는다. 두 저장소의 `feat/weekly-admin-controls` 변경을 함께 검토한다.

1. 운영 백업과 현재 배포 SHA를 확인한다. 현재 마이그레이션 목록을 조회하고 누락분만 적용한다. GFC 기존 `public` 업무 테이블/경매 데이터는 변경하지 않는다.
2. StartupRadar의 `20260914153311_weekly_admin_controls.sql`이 선행되어야 한다. 이어 `20260914155222_opportunity_discovery.sql`, `20260914174024_expanded_official_channels.sql`을 순서대로 적용한다. GFC의 `tests/fixtures/radar-migrations`는 테스트 복사본이며 두 번 적용하는 파일이 아니다.
3. 서버 비밀 환경에서 `python -m radar.cli seed-institutions`를 실행한다. 25개 후보와 검토된 채널을 **비활성**으로 추가하고 기존 기관·채널 설정을 덮어쓰지 않는다. 기존 `seed-sources`로 운영 설정을 다시 덮어쓰지 않는다.
4. GFC 웹과 StartupRadar 워커를 함께 배포한다. 기존 DB/공공 API/Telegram 비밀값은 서버에 유지한다. 프런트엔드에는 기존 Supabase 공개 URL·anon key만 사용한다.
5. 관리자가 로컬 검증에 성공한 채널 중 운영할 대상을 활성화한다. 첫 `DISCOVER`를 수동 실행해 채널 상태·실제 자료를 확인한 뒤 매일 수집과 주간 요일·시간을 저장한다. 공식 API 두 곳의 기존 인증·페이지 상한도 확인한다. 기본값은 페이지당 100건·최대 100페이지이며 K-Startup의 모집 중 질의 및 기업마당 API 제공 범위 밖 자료는 포함을 보장하지 않는다. 페이지 상한 도달·반복·누락은 부분 수집/오류로 표시한다.
6. GitHub `RADAR_V2_ENABLED=true`가 있어야 예약 워커가 작동한다. 기존 `RADAR_V2_DELIVERY_ENABLED` 및 구독 상태는 임의 변경하지 않는다. 이번 검증에는 실제 Telegram 발송이 필요하지 않다.

수동 명령: `python -m radar.cli discover`는 수집만 한다. `python -m radar.cli weekly --from-catalog --draft`는 저장 자료로 초안을 만든다. `python -m radar.cli calendar`는 두 예약을 확인한다. `--deliver`는 별도 운영 승인 없이 테스트에 사용하지 않는다.

복구 시 신규 채널과 매일 수집을 먼저 비활성화하고 예약 실행 상태를 확인한다. 워커와 웹을 직전 주간 관리 버전으로 되돌린다. 새 테이블·정정·원문 이력은 삭제하지 않는다. 새 게시 제외 보호 정책도 유지하면 기존 고급 목록에 제외된 자료가 노출되는 것을 막는다. 중단된 소유권은 기록된 PID/Actions 실행 종료를 확인한 다음 기존 `recover-execution --confirm-stopped` 절차로만 해제한다. 불확실한 Telegram 발송 건은 재시도하지 않는다.

## 구현 범위와 남은 연결 작업

일반 HTML/RSS/고정 페이지, 한양대 공식 공개 상세 API, 블루포인트 선택적 브라우저와 후보 연결 인터페이스를 구현했다. 전용 뉴스레터 수신함과 검색 공급자는 연결하지 않았다. PDF·이미지 중심 공고는 원문 링크와 정보 부족 또는 읽기 실패 상태로 남는다. 기존 AI/OCR 도구는 유지하지만 매일 기본 수집·주간 발행의 필수 의존성으로 만들지 않았다. 이러한 출처의 미완성은 다른 정상 출처를 중단시키지 않는다.

한 채널당 읽기 호출 최대 60회·소프트 시간 예산 240초, 요청 간 최소 1초, 페이지 최대 5개·신규 항목 최대 100개, 활성 상세 재확인 최대 20개를 오래된 확인 순으로 순환한다. 진행 중인 요청은 개별 타임아웃까지 더 걸릴 수 있다. 현재 기본 채널은 더 작은 범위를 사용한다. 요청별 12초·3MB 상한과 기존 일시 장애 재시도 1회, HTTPS·DNS·리다이렉트의 공인 허용 호스트 검사 및 robots 확인을 적용한다. 세부 범위는 `institutions.json`과 수집 건강도에 표시한다. 수집 범위·상한은 넓힐수록 실행 시간과 출처 부하가 증가한다.

## 2026-09-15 추가 기관을 설치하는 경우

[확대 결과·기관별 범위·배포 순서](OPPORTUNITY_EXPANSION.md)에 따라 `seed-institutions --update-reviewed`를 사용한다. 이전 배포본의 검토 내용과 정확히 일치하는 기관만 명시적으로 갱신하고, 사용자 수정은 `review_conflicts`로 남긴다. 기본 설치는 기존 검토를 갱신하지 않는다. 새 채널은 어느 명령에서도 자동 활성화되지 않는다.

블루포인트 브라우저 채널을 운영할 서버에만 `requirements-browser.txt`와 Chromium을 설치한다. GitHub Actions의 선택적 설치 변수는 `RADAR_BROWSER_ENABLED=true`다. 의존성 미설치는 ‘설정 필요’이며 ‘신규 공고 없음’이 아니다. 브라우저는 GET·허용 호스트·robots 검증과 자원 상한을 적용하며 신청 폼·이메일을 제출하지 않는다.

과거 연도 공고의 마감일이 미확인이면 전체 목록에는 ‘확인 불가’로 남고 주간 공지에서 제외된다. 관리자 정정 화면에서 공식 근거에 맞는 마감일을 저장해야 다시 주간 선정 대상이 될 수 있다. 이메일 접수 안내는 공식 원문에서 확인하고, 웹 신청 링크가 있는 것처럼 표시하지 않는다.
