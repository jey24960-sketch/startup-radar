# GFC profile commands and calculation requests

Phase A now converts POST team creation and PATCH profile editing to Supabase RPC. Together with the earlier four reads, these member operations do not require a Python HTTP origin. Notification preferences and admin health still await conversion; the final API decision is not yet complete.

## Atomic mutation boundary

`public.gfc_radar_update_profile` is SECURITY INVOKER. It checks the existing GFC role and Radar OWNER/EDITOR membership, locks the current profile and requires the submitted expected version to match. It applies preset defaults only to previously assumed/unknown fields, then explicit edits. SQL validates the generated Python profile contract, preserving null as UNKNOWN and false as known false. The server returns the new version and calculation PENDING, not a claimed eligibility result.

Before/after triggers on Radar profile tables enforce the version increment, validate values, append the immutable profile snapshot and insert one calculation request per team/version in the same transaction. Any queue/history failure rolls back the profile update. Existing Python create/save methods use these triggers too; they no longer insert history a second time. There are no changes to public.profiles or existing GFC teams. The new migration and updated Python code must be deployed together before running V2; an older Python worker that manually inserts the same history row would encounter a duplicate key. V2 remains disabled during this transition.

The authoritative profile contract is generated by `python -m tools.profile_contract` from TeamProfile/PRESETS. Tests compare the stored contract and SQL preset/update results with the Python engine and cover invalid types/ranges/dates, explicit overrides, null, false and version concurrency. SQL accepts strict JSON types, limits profile JSON to 64 KiB and arrays to 100 entries. These resource bounds are stricter than unconstrained Python text/list fields. The eligibility engine itself is not duplicated in SQL.

## Team creation and privilege scope

`public.gfc_radar_create_team` is an invoker wrapper over private `startup_radar.create_member_team`. This one private SECURITY DEFINER function is necessary for atomic team/owner bootstrap before membership exists. It checks auth.uid() and protected public.my_role(), accepts only name, preset and a client request UUID, and always binds OWNER to the authenticated caller. It cannot set GFC roles, choose another owner, modify existing teams or access external secrets. All identifiers and schema paths are fixed. PUBLIC/anon execution is revoked and only the exact needed functions are granted to authenticated; trigger functions have no public execution grants.

The private team_creation_requests table records request UUID, actor and result. Reusing the same UUID and payload returns the same team; another actor or changed payload is rejected. The current form retains the UUID across failed responses/retries until success or changed inputs. Reloading the page discards that in-memory retry key, so users should first check the team list after an uncertain save followed by reload. No arbitrary duplicate team-name restriction is imposed.

The table deliberately has RLS enabled with no client grants/policies: only the narrowly authorized bootstrap function and backend can access it. Supabase reports one additional RLS-no-policy INFO for that intended default deny. No new security WARNING was introduced. See [Supabase function security](https://supabase.com/docs/guides/database/functions) and [RLS default-deny guidance](https://supabase.com/docs/guides/database/database-linter?lint=0008_rls_enabled_no_policy).

## Queue processing

`profile_calculation_requests` has a primary key of team/version and an FK to the immutable profile history. A member can read own-team requests; only an owner/editor can insert the current version, and column grants prevent forging worker state, attempts or timestamps. State transitions are PENDING → RUNNING → SUCCESS/FAILED; obsolete versions become SUPERSEDED. The batch worker tracks attempts and redacted error class names.

REFRESH still handles presets, new program versions and daily invalidation as well as profile requests. It marks the captured team/version request while computing. If the profile changes during calculation, it supersedes that request and leaves the new version pending; the next refresh picks it up. Existing read guards hide stale result versions immediately. Interrupted RUNNING requests can be retried by the serialized batch, with no Telegram side effect. Queue failure, concurrent writes and a profile edit during computation are tested.

The worker currently scans all current team scopes and retained program versions, skipping current cached results; the queue is durable tracking, not yet a bounded queue-only worker. Runtime/storage still scale with teams and history. Schedules remain disabled, and no automatic latency guarantee applies until real runtime credentials and operating validation are complete.

## GFC UX and remaining work

The profile form loads independently of notification preferences, so the remaining compatibility HTTP preference path cannot block creating or editing a profile. A version conflict offers an explicit reload before retrying. Saved feedback waits for the next calculation. Browser tests cover no Python origin, conflict reload and same-key creation retries; these are fixtures, not live Google OAuth acceptance.
