# 공식 수집 경로 확대 결과 — 2026-09-15

## 학회장이 알아야 할 결과

공공 API 2곳을 유지하면서, 조사한 후보 25개 기관 중 **실제 원문 읽기를 확인한 기관을 6곳에서 20곳으로, 채널을 10개에서 26개로 늘렸다.** 기관 전체의 모든 공고가 연결된 것은 아니다. 스파크랩은 소개 페이지 변경 감시이고, 한양대는 일부 이미지 공고를 읽지 못한 부분 수집이다. 실제 모집 자료를 제공한 기관은 19곳이다.

이번에 추가한 14개 기관의 경로는 공식 홈페이지의 공개 API, 별도 공식 게시판, 프로그램 페이지를 우선 사용한다. 일반 HTML로 내용이 나오지 않는 블루포인트에만 선택적 브라우저 읽기를 적용했다. 기존 주간 발행 요일·시간 설정, 공지 정정, 원문 이력, 회원·관리자 권한, Telegram 중복 방지 기능 위에 통합했다.

**코드와 로컬 검증까지 완료했다. 운영 DB·웹·워커에는 아직 적용하지 않았고, 운영 수집이나 Telegram 발송을 활성화하지 않았다.** 두 저장소의 기존 `feat/weekly-admin-controls` 브랜치와 draft PR #9(Radar), #11(GFC)에 이어지는 변경이다. 작업 시작 코드는 각각 `5bbf112`, `68b3139`였고 작업 트리는 깨끗했다.

## 실제 수집에서 회원 목록·주간 공지까지의 검증

공식 공개 페이지를 채널별 최대 1~5건만 읽었다. 일부 목록은 첫 페이지 또는 특정 프로그램 영역으로 제한했다. 합계 **36건 시도, 35건 읽기 성공, 1건 실패**다. 이 수치는 읽기 성공률의 표본이며, 목록 바깥의 누락을 전수 대조한 수치가 아니다. 전국 포괄률이나 기관 전체 공고 누락률로 해석할 수 없다.

한 번 읽은 원문을 격리된 로컬 DB에 재현하여 불필요한 외부 재요청을 줄였다. 운영 DB, 운영 공지, 실제 사용자 인증 계정은 사용하지 않았다.

| 검증 단계 | 결과 |
|---|---|
| 공통 저장·분류 | 원문 35건 저장, 결과 발표 1건 제외, 확인된 모집 정보 34건 |
| 회원 목록 | 일반 회원 권한 RPC에서 34건 조회, 실제 상세 3건 조회 확인 |

| 정보 충실도 | 마감일 확인 17/34, 웹 신청 링크 확인 16/34. 이메일 접수는 웹 링크 비율에 포함하지 않음 |

예를 들어 한양대 창업동아리 모집은 공식 목록 → 공개 상세 API → 확인된 신청 마감 9월 17일 → 회원 모집 목록으로 이어졌다. 프라이머의 한 페이지는 세 개 모집으로 분리되고 서로 다른 기수·일정이 보존됐다. 고려대 시상 결과는 원문 저장 후 모집 목록에서 제외됐다. 삼성·롯데의 과거 공고는 현재 모집인 것처럼 소개하지 않았다.

날짜가 없다는 이유만으로 마감·상시로 추정하지 않는다. 과거 연도이고 마감이 미확인인 공고는 상세에서 확인할 수 있으나 관리자가 근거를 확인하고 마감을 정정하기 전까지 주간 공지에서 제외한다. 확인 불가 공고는 운영자가 검토해야 하며, 수집 성공은 회원의 신청 자격을 보증하지 않는다.

## 변경에 직접 관련된 테스트

- 확대 경로·날짜·기수·결과 발표 제외·관리자 권한·원문 보존·브라우저 GET 제한·설정 설치 검증: 최종 `tests/test_channel_expansion.py` **20개 통과**.
- 기존 수집·주간 관리 관련 묶음: 초기 54개 통과 뒤 테스트 픽스처 1개 오류를 수정했다. 후속 주간 회귀 15개 통과 뒤 관리자 입력 허용 필드 테스트를 수정하고, 브라우저 활성화에 서버 준비 조건을 추가했다.
- 최종 관리자 활성화 + HTTP robots·출처 장애 회귀 **28개 통과**. 실패했던 확대 테스트는 위 최종 20개 실행에 포함되어 통과했다.
- GFC Node 테스트 **83개 통과**, 최종 웹 빌드 성공. 기존 번들 크기·Browserslist 안내는 남는다. 최종 SQL의 브라우저 준비 조건은 Python의 실제 로컬 DB 테스트에서 확인했다.
- 요청 속도 제한을 넣은 최종 브라우저로 블루포인트 원문 1건을 다시 읽어 성공했다. 전체 기관을 반복 재수집하지 않았다.

이번에 전체 Python 회귀를 다시 돌렸다고 보고하지 않는다. 이전 구현의 전체 회귀 결과와 UI 검증 이력은 최초 보고서에 있으며, 이번에는 달라진 수집 경로·권한·주간 조합과 웹 빌드에 집중했다. 회원·관리자 테스트는 격리된 DB 역할을 사용하며 실제 운영 계정 검증과 구별한다.

1. 기존 백업·배포 버전을 확인하고 선행 마이그레이션 `20260914153311_weekly_admin_controls.sql`, `20260914155222_opportunity_discovery.sql` 이후 **`20260914174024_expanded_official_channels.sql`**을 적용한다. 새 마이그레이션은 관리자 채널 저장 함수에 준비된 브라우저 채널의 활성화를 허용한다. 인증·관리자·공식 호스트·동시 수정 검사와 감사 이력은 유지한다. GFC의 동일 이름 파일은 테스트 복사본으로 운영에 중복 적용하지 않는다.
2. StartupRadar 워커와 GFC 웹을 함께 배포한다. 서버 비밀값은 프런트엔드에 넣지 않는다. 블루포인트를 사용할 서버에만 `pip install -r requirements-browser.txt`와 `python -m playwright install --with-deps chromium`을 실행한다. GitHub Actions는 저장소 변수 `RADAR_BROWSER_ENABLED=true`일 때만 이 선택적 설치를 수행한다. 일반 HTML·공공 API·주간 발행은 브라우저를 필수로 요구하지 않는다.
3. 서버 환경에서 `python -m radar.cli seed-institutions --update-reviewed`를 실행한다. 새 채널은 모두 비활성이다. 이전 배포본의 정책·호스트·검토 메모와 정확히 일치하는 기관만 이번 공식 검토로 갱신하고 감사 이력을 남긴다. 운영자의 별도 수정은 보존하고 `review_conflicts`로 알린다. 옵션 없는 기본 설치는 기존 기관 검토를 갱신하지 않는다.
4. 관리자의 **수집·검토 관리**에서 필요한 채널을 활성화하고 매일 수집 시간을 확인한다. 브라우저 채널은 개발자가 준비 선택자를 설치해야 활성화할 수 있다. 런타임이 없다면 ‘설정 필요’로 실패하며 정상 연결로 표시하지 않는다. 첫 운영 수집 결과에서 성공·부분 수집과 오류를 확인한다.
5. **발행 일정·공지 정정**에서 기존 주간 요일·시간을 확인한다. 기존 `RADAR_V2_ENABLED`, 발송 허용 변수와 구독·채널 상태를 보존한다. 테스트 목적으로 발송을 켜지 않는다.

브라우저는 새 격리 세션에서 GET 읽기만 사용하며 모든 요청을 기존 공개 호스트·DNS·HTTPS·robots 검사를 통과시킨다. POST·PUT, WebSocket, 서비스 워커, 다운로드를 막고 쿠키를 사용자 세션에서 가져오지 않는다. 브라우저 렌더링마다 최대 80개 요청·20MB·소프트 40초, 개별 HTML 3MB, 네트워크 읽기 간 최소 1초를 적용한다. 채널 전체 60회 읽기·소프트 240초 및 기존 개별 타임아웃도 유지한다. 진행 중 요청 때문에 소프트 제한보다 늦게 끝날 수 있다.

복구는 새 채널을 비활성화하고 선택적 브라우저 변수를 해제한 뒤 직전 워커·웹 버전으로 되돌린다. 기존 공고·정정·원문 이력은 삭제하지 않는다. 추가 함수 마이그레이션은 이전 경로와 호환되므로 데이터 삭제나 일괄 다운 마이그레이션으로 복구하지 않는다.

## 비개발자가 운영하는 방법

회원은 **전체 모집**에서 모집 상태·유형·대상 단계·지역을 고르고 상세의 공식 원문을 확인한다. **상시 프로그램**은 따로 본다. 이메일 접수 공고는 원문에 안내된 방법을 사용한다. 시스템이 신청서를 대신 제출하지 않는다.

학회장은 **수집·검토 관리**에서 마지막 성공과 실패 이유를 보고, 검토함에서 미확인 날짜·분류·중복을 정정한다. 수정 사유와 이전 값은 남는다. 원문 변경이 정정과 충돌하면 검토 안내가 표시된다. **발행 일정·공지 정정**에서는 주간 요일·시간을 바꾸거나 이미 발행된 웹 공지를 수정한다. 이미 전송된 Telegram 메시지는 자동 수정·재전송하지 않는다.

새 기관 주소를 넣는 것만으로 자동 연결되지는 않는다. **연결 요청**으로 등록하면 개발 담당자가 공식 관계·접근 정책·본문 읽기를 확인해야 한다. 전체 운영 절차와 기존 제한은 [운영 안내](OPPORTUNITY_OPERATIONS.md)를 따른다.
