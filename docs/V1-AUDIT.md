# StartupRadar 상세 소개: 구조·기능·운영·한계

확인일: 2026-09-12. 저장소: [jey24960-sketch/startup-radar](https://github.com/jey24960-sketch/startup-radar). 브랜치: main. 커밋: `c18f84048ddd08adca10d44b83692a1060d957cb`(2026-06-02 23:38:26 KST). 원격 main과 로컬 코드가 일치함을 확인했다.

이 문서는 README보다 실제 실행 코드를 우선한다. 코드 검토와 제한적인 오프라인 재현을 수행했으며, 실제 배포·수집 성공률·AI 응답 품질·텔레그램 전달 상태는 검증하지 않았다. 기능 수정이나 운영 설정 변경은 수행하지 않았다.

## 1. 프로그램 개요

StartupRadar는 대학생 창업동아리와 예비창업팀을 위해 창업 지원정보를 수집하고, AI로 분석해 텔레그램으로 전달하는 자동화 프로그램이다. 여러 기관의 웹사이트를 반복해서 확인하는 부담을 줄이고, 팀의 현재 상황에 맞는 지원 기회를 검토하도록 돕는 것이 목적이다.

정부·공공기관, 대학 창업지원단, 액셀러레이터와 재단의 웹페이지 또는 RSS에서 텍스트를 모은 뒤 Claude가 지원 대상, 지원금이나 혜택, 마감일, 신청 링크, 추천 이유 등을 구조화한다. 동아리 프로필에 따라 적합도를 평가하고 기준 점수 이상인 공고를 선별한다. 과거 발송 이력과 대조해 새로운 공고를 텔레그램에 전달한다.

관리자는 텔레그램에서 수집 실행, 팀 단계 변경, 정기 실행 중지를 요청할 수 있다. GitHub Actions가 수집·분석 작업을 실행하고 Cloudflare Worker가 명령을 받는다. 별도 상시 실행 서버를 직접 관리할 필요는 줄지만, 서비스 계정·시크릿·배포·장애 대응은 필요하다.

현재 프로필은 서울 소재 대학 연합 창업동아리, 팀당 3~5명, MVP 단계, 사업자등록 전 예비창업팀이다. IT·테크·소셜벤처·플랫폼과 글로벌 진출에 관심을 두며, 100만원~1억원 규모의 지원 기회가 프로필에 기재되어 있다. 이 조건은 모델에 전달되는 설명이며 금액·지원 자격을 엄격히 검증하는 규칙 엔진은 아니다.

## 2. 전체 구조와 실행 경로

```text
텔레그램 관리자
    │ 명령
    ▼
Cloudflare Worker — webhook 수신·관리자 ID 확인
    ├─ /run, /dry → GitHub Actions 수집 workflow 요청
    ├─ /stage → config.py 단계 수정·커밋·푸시
    └─ /stop → 정기 실행 플래그 수정·커밋·푸시

GitHub Actions 정기 일정 또는 수동 실행
    │ 정기 실행이면 .startup_radar_auto_run 검사
    ▼
Python main.py
    ├─ 필수 환경변수 검증
    ├─ 발송 이력 정리
    ├─ core/crawler.py: 13개 소스 텍스트 수집
    ├─ core/analyzer.py: Claude 분석·중복 제거·점수 필터
    ├─ core/deduplicator.py: 이미 보낸 공고 제외
    ├─ JSON 결과 저장
    ├─ core/notifier.py: Telegram 메시지 구성·발송
    └─ 발송 성공 시 이력 기록

Actions 캐시: 발송 이력 복원·저장
Actions 아티팩트: 로그·결과 보관
```

Worker는 공고를 직접 분석하지 않고 GitHub 작업 실행을 요청한다. 따라서 명령 접수 응답과 실제 수집 완료는 별개다. 정기 실행은 Worker를 거치지 않는다.

| 파일 | 역할 |
|---|---|
| `main.py` | 전체 파이프라인, 결과 저장, 발송 성공 후 이력 처리 |
| `config.py` | 동아리 프로필, 모델, 수치 설정, 수집 URL, 저장 경로 |
| `core/crawler.py` | requests·BeautifulSoup·XML 파서 기반 수집 |
| `core/analyzer.py` | Claude 호출, JSON 파싱, 적합도 필터 |
| `core/deduplicator.py` | JSON 기반 발송 이력 관리 |
| `core/notifier.py` | 마감 표시, URL 제한, 메시지 분할·발송 |
| `cloudflare_worker.js` | webhook, 관리자 확인, 명령별 workflow 요청 |
| `.github/workflows/startup_radar.yml` | 정기·수동 수집, 캐시, 아티팩트 |
| `.github/workflows/update_stage.yml` | 현재 단계 수정·커밋·푸시·완료 알림 |
| `.github/workflows/update_auto_run.yml` | 정기 실행 상태 파일 수정·커밋·푸시 |
| `.github/workflows/telegram_polling.yml` | 이전 polling 경로. 자동 일정은 제거됐지만 수동 실행 정의는 남음 |
| `.startup_radar_auto_run` | 정기 실행 허용 여부. 확인한 값은 false |

루트에도 `crawler.py`, `notifier.py`, `deduplicator.py`, `startup_radar.yml`이 남아 있다. 현행 main은 `core/`를 import하고 Actions는 `.github/workflows/` 정의를 사용한다. 루트 파일을 고쳐도 현재 실행에는 반영되지 않을 수 있다. 루트 크롤러는 현재 config에 없는 API 키 상수를 import하는 등 이전 설정 방식과 결합되어 있다.

## 3. 수집 범위

| 분류 | 현재 등록된 소스 |
|---|---|
| 정부·공공 2개 | K-Startup, 서울산업진흥원 |
| 대학 5개 | 고려대, 한양대, 경희대, 동덕여대, 숙명여대 창업지원단 |
| 액셀러레이터·VC 4개 | 스파크랩, 프라이머, 매쉬업엔젤스, 퓨처플레이 |
| 재단·임팩트 2개 | 아산나눔재단, 카카오임팩트 |

실제 SOURCES 항목은 13개다. 등록 URL에는 공고 목록뿐 아니라 홈페이지, 프로그램 페이지, 포트폴리오 페이지가 섞여 있다. 등록된 기관의 모든 공고를 수집하는 구조는 아니다.

각 소스 URL 한 곳을 순차 요청한다. HTML에서는 내비게이션·헤더·푸터·스크립트 등의 요소를 제거하고 제목·문단·목록·표·링크·div 등의 텍스트를 추출한다. 같은 문자열은 중복 제거하지만 부모 요소와 자식 요소에 포함된 내용은 부분적으로 반복될 수 있다. 소스별 추출 결과는 앞 3,000자로 제한한다.

고려대 URL은 RSS다. XML에서는 title, description, link, summary의 텍스트를 읽는다. RSS 판단은 URL에 `rss`가 포함되는지에 의존한다. Atom의 링크 속성처럼 다른 형식은 충분히 처리하지 못할 수 있다.

HTTP 요청 제한시간은 10초다. 403 또는 연결 오류는 3초 후 한 번 재시도하며, 소스 사이에 0.5초 대기한다. 실패한 소스는 기록하고 다음 소스를 계속 처리한다. 브라우저와 유사한 User-Agent를 사용하고 리다이렉트를 허용한다.

브라우저 렌더링, 상세페이지 순회, 페이지네이션, 첨부 PDF/HWP 분석은 없다. 자바스크립트로 표시되는 내용이나 첨부파일에만 있는 조건, 다음 페이지의 공고는 놓칠 수 있다.

## 4. AI 분석과 결과 데이터

수집한 소스 텍스트를 약 10,000자 단위로 묶어 Claude에 전달한다. 소스 하나를 유지하면서 묶음을 나누며 정확한 토큰 기준 분할은 아니다. 설정 모델은 `claude-sonnet-4-5`, 최대 응답 토큰은 8,192다. 이는 코드 설정이며 모델 제공 상태나 가격을 별도로 확인한 것은 아니다.

프롬프트는 현재 모집 중이거나 예정된 공고를 추출하고, 예비창업팀 지원 가능성을 우선하며, 사업자등록 필수 공고는 20점 이하로 평가하도록 지시한다. 동아리 프로필과 실행 날짜도 전달한다.

| 필드 | 의미 |
|---|---|
| title / organization / source | 프로그램명, 주관기관, 수집 소스 |
| type | 지원사업·경진대회·액셀러레이터·보조금·대학지원·투자연계 |
| target | 지원 대상과 조건 |
| amount | 지원금 또는 혜택 |
| deadline | 마감일. 알 수 없으면 null |
| apply_url | 신청 또는 공고 URL |
| summary | 동아리에 유용한 이유 요약 |
| relevance_score / relevance_reason | 적합도 점수와 판단 근거 |
| stage_fit | 팀빌딩·아이디어·MVP·초기매출 중 관련 단계 |

모델 응답에서 JSON 코드블록을 제거하고 배열을 추출한다. 잘린 응답은 마지막 완전한 객체까지 복구하려고 시도한다. 공고는 점수 내림차순으로 정렬한 뒤 제목+기관을 기준으로 중복 제거하고, 60점 미만을 제외한다.

필드별 타입, 필수값, 점수 범위, 날짜 형식을 포괄적으로 검증하는 스키마는 없다. 마감 공고 제외도 주로 모델 지시에 의존하며 분석 후 날짜로 강제 제거하지 않는다. 적합도는 모델의 판단으로, 실제 지원 자격이나 선정 가능성을 보증하지 않는다.

## 5. 알림과 중복 관리

메시지는 날짜, 수집 소스 수, 신규 공고 수, 실패 수와 함께 공고 제목·기관·마감 잔여일·점수·혜택·요약·허용된 링크를 표시한다. target, relevance_reason, stage_fit, type이 JSON에 있어도 메시지에서 모두 별도 항목으로 보여주지는 않는다.

- 마감 임박은 기본 D-7 이내이며 별도 섹션에 표시한다.
- 일반 추천은 최대 7건이다. 임박 섹션에는 이 제한이 적용되지 않아 전체 건수는 7건을 넘을 수 있다.
- 오늘 마감, D-7 이내, D-14 이내를 구분한다.
- 메시지가 4,096자를 넘으면 줄 단위로 나누고, 한 줄 자체가 길면 강제로 자른다.
- 신규 공고가 없어도 일반 실행에서는 안내 메시지를 보낸다.

신청 링크는 HTTP/HTTPS인지, 소스 도메인 또는 그 하위 도메인인지 확인한다. 공백, 과도한 길이, 일부 Markdown 문자가 포함된 링크는 제거한다. 소스가 불명확하면 등록된 전체 소스 도메인을 기준으로 검사한다. 이는 허용 도메인 제한이며 링크가 실제 공고로 연결되는지 확인하는 검증은 아니다.

발송 DB는 `data/seen_programs.json`이다. 제목+기관+신청 URL 문자열의 해시 앞 12자리를 키로 사용하며 제목·발송 시각·마감일을 기록한다. 최근 90일의 발송 기록을 유지하고 발송 시각으로 정리한다. 함수 설명과 달리 실제 마감일 기준 삭제는 아니다.

URL이 바뀌면 같은 공고도 다시 알림할 수 있고, 제목·기관·URL이 같으면 마감 연장이나 금액 변경을 새 정보로 인식하지 못한다. 이미 보낸 공고를 마감 직전에 다시 알리는 독립 리마인더도 없다.

## 6. 명령과 운영 방식

| 명령 | 실제 동작과 의미 |
|---|---|
| `/run` | main 브랜치 수집·발송 작업 요청. 접수 응답은 완료를 뜻하지 않음 |
| `/dry` | 수집·Claude 분석 수행, 공고 결과 발송 생략. 비용 없는 미리보기가 아님 |
| `/stop` | 정기 실행 플래그를 false로 만드는 작업 요청. 실행 중인 작업 취소는 아님 |
| `/stage 단계` | config의 현재 단계 수정·커밋·푸시. 다음 수집에 적용 |
| `/share` | 수신 설정 안내. 설정을 자동 변경하지 않음 |
| `/id` | 사용자·대화 ID 안내. 관리자 인증보다 먼저 처리 |
| `/status` | 고정된 정상 작동 문구. 서비스 전체 상태 조회는 없음 |
| `/help` | 명령 목록과 메뉴 등록 시도 |

Worker는 `from.id`로 관리자를 확인하고 쉼표로 구분한 여러 관리자 ID를 지원한다. 관리자 설정이 없으면 결과 수신 chat ID를 대신 사용한다. 그룹·채널 ID와 개인 ID는 구분해야 한다.

정기 실행 일정은 화·금 오후 3시 KST다. 현재 `.startup_radar_auto_run`은 false이므로 해당 코드 상태의 정기 수집은 건너뛴다. 수동 실행은 이 상태를 무시한다. 재개용 텔레그램 명령은 없고 `update_auto_run.yml`을 enabled=true로 실행하는 경로가 있다.

Python은 ANTHROPIC_API_KEY, TELEGRAM_BOT_TOKEN, TELEGRAM_CHAT_ID를 필수로 읽는다. `--dry`에도 모두 필요하다. 인자 파싱보다 시크릿 검증이 앞서므로 환경변수가 없으면 `--help`도 영향을 받는다.

Worker는 GITHUB_TOKEN, GITHUB_OWNER, GITHUB_REPO, TELEGRAM_BOT_TOKEN, TELEGRAM_CHAT_ID, TELEGRAM_ADMIN_CHAT_ID를 사용한다. Worker 토큰은 workflow 요청에 쓰이고, 설정 변경 workflow는 작업 토큰으로 저장소에 푸시한다. 권한·브랜치 보호 규칙에 따라 성공 여부가 달라질 수 있다.

실제 공고 수신 대상은 Python 작업이 읽는 GitHub Actions의 TELEGRAM_CHAT_ID다. Worker의 동일 이름 Secret만 바꾸면 공고 대상은 바뀌지 않는다. 현재 Worker `/share` 안내는 Worker 설정 변경만 안내하므로 보완이 필요하다.

Actions는 Python 3.12·Ubuntu 환경을 사용한다. Python 의존성은 anthropic, requests, beautifulsoup4, lxml, defusedxml이며 버전 하한만 명시되어 있다. 잠금 파일은 발견하지 못했다.

## 7. 저장·비용·확장성

신규 공고가 있으면 `data/report_YYYYMMDD_HHMM_new.json`에 저장한다. 같은 분에 같은 위치에서 실행하면 파일명이 겹칠 수 있다. 신규 결과가 없으면 새 보고서를 저장하지 않는다. 원본 수집 텍스트와 모델 원문 응답을 함께 보존하지는 않는다.

로그는 `logs/startup_radar.log`에 남는다. Actions는 로그 14일, 결과 아티팩트 30일 보관을 설정한다. 발송 DB는 실행별 캐시 키와 공통 복원 접두어로 이어간다. 영구 DB의 트랜잭션이나 동시성 보장을 제공하는 구조는 아니다.

AI 사용량은 실행 빈도·입력량·묶음 수·응답 길이에 따라 달라진다. 적합도 임계값은 AI 호출 뒤 적용되므로 점수를 높이는 것만으로 분석 비용을 줄이지 못한다. 실행 주기, 입력량, 변경된 자료만 분석하는 방식이 비용에 더 직접적으로 관련된다. 현재 가격이나 계정 한도를 검증하지 않았으므로 README의 무료 운영·월 비용 추정을 확정값으로 사용하지 않는다.

소스가 늘면 순차 수집 시간과 분석량이 늘어난다. 비동기 수집, 조건부 요청, 본문 변경 감지, 원문 캐시가 없다. 프로필과 결과 수신 대상은 공통 설정이므로 한 동아리 또는 한 운영 단위에 맞는다. 그룹 공유는 가능하지만 개인별 맞춤 구독·팀별 독립 프로필·웹 대시보드는 없다.

## 8. 주요 한계와 결함

아래 항목은 구현 사실과 코드에서 추론되는 영향을 구분해 읽어야 한다. 실제 서비스 사고가 발생했다는 의미는 아니다.

### 8.1 우선 수정할 항목

**미발송 공고를 발송 완료로 기록할 수 있다.** 일반 추천을 7건으로 자르지만 main은 신규 목록 전체를 mark_as_sent에 전달한다. 일반 공고 9건으로 메시지 생성 함수를 오프라인 실행하면 7건만 포함되며, 코드상 9건 전체를 기록하는 경로가 확인된다. 빠진 2건은 이후 이미 보낸 공고로 제외될 수 있다. 실제 전송한 항목만 기록하거나 남은 항목을 대기열에 보존해야 한다.

**AI 오류와 정상 빈 결과가 구분되지 않는다.** `_call_claude()`는 API·파싱 오류에 빈 리스트를 반환하고, analyze는 None이 아니면 성공으로 센다. 오류 반환을 빈 리스트로 모사했을 때 결과가 `([], False)`여서 실패 플래그가 켜지지 않았다. API 장애가 ‘새 공고 없음’으로 보일 수 있다. 데이터와 오류 상태를 분리해야 한다.

**webhook 발신자 검증이 없다.** Worker는 JSON의 from.id를 비교하지만 webhook 시크릿 헤더를 검증하지 않는다. 별도 보호가 없다면 요청 본문의 신원을 신뢰하는 구조다. Worker 바깥의 인프라 보호 유무는 확인하지 않았다. 실제 공격 실험 없이 코드상 보완 필요성을 확인한 것으로, webhook 시크릿 검증을 우선 검토해야 한다.

**실패가 Actions 성공으로 보일 수 있다.** 전체 수집 실패나 발송 실패 일부 경로는 로그를 남기고 반환하며 비정상 종료 코드를 지정하지 않는다. 프로세스가 정상 종료하면 Actions가 성공으로 표시할 수 있다. 실패 유형을 분리하고 작업 종료 상태에 반영해야 한다.

### 8.2 수집·분석 정확도

1. **원문 범위 부족:** 소스당 앞 3,000자 제한, 중첩 텍스트, 홈페이지 중심 URL 때문에 중요한 공고가 입력에 없을 수 있다. 상세페이지와 첨부도 탐색하지 않는다.
2. **HTML 링크 손실:** 표시 텍스트만 뽑고 href를 보존하지 않는다. 모델 입력에 소스명과 본문은 있지만 원본 URL·링크 목록을 체계적으로 붙이지 않아 신청 URL을 추정할 수 있다.
3. **도메인 검사 한계:** 허용 도메인의 틀린 경로는 통과할 수 있고 기관이 쓰는 외부 신청 플랫폼은 차단될 수 있다. URL 제한과 사실 검증은 별도 설계가 필요하다.
4. **자격·마감 검증 부족:** 조건 판정과 마감 공고 제외가 프롬프트에 의존한다. 이미 지난 마감일이 남아 알림에 ‘마감됨’으로 표시될 수 있다.
5. **스키마 부재:** 배열 안에 문자열, 점수에 문자열/null, 요약에 null 등이 있으면 정렬·비교·문자열 처리에서 예외가 날 수 있다. 잘못된 항목만 격리하는 처리가 필요하다.
6. **JSON 복구 취약성:** 대괄호 카운팅이 문자열 내부 괄호와 이스케이프를 구분하지 않는다. 마지막 중괄호 기준 복구도 모든 잘린 응답을 처리하지 못한다.
7. **단순 중복 기준:** 제목 표기·추적 URL 변화는 재알림을 만들고 마감 연장은 놓칠 수 있다. 분석 단계는 제목+기관, 발송 이력은 제목+기관+URL로 기준도 다르다.
8. **외부 본문 영향:** 수집 텍스트가 모델 입력에 그대로 들어가고 출력 검증이 약하다. 잘못되거나 악의적인 본문이 판단에 영향을 줄 가능성이 있으며 실제 악성 입력 실험은 하지 않았다.

### 8.3 발송·운영 신뢰성

1. **부분 발송 후 재알림:** 여러 메시지 중 하나라도 실패하면 전체 이력 기록을 생략한다. 다음 실행에서 이미 전달된 공고도 다시 보낼 수 있다.
2. **발송 재시도 부족:** Telegram 전송에 재시도·속도 제한 대기 처리가 없다. 긴 줄 강제 분할은 Markdown 구문 중간을 자를 수 있다. Claude도 애플리케이션 차원의 복구 정책과 SDK 기본 동작을 구분해야 한다.
3. **상태 확인의 오해:** `/status`는 최근 작업·API·자동 실행 상태를 확인하지 않고 고정 문구만 반환한다.
4. **다음 일정 안내 오류:** 알림 하단은 정기 실행이 꺼져 있어도 다음 화·금 15시를 안내한다. 일정 변경 시 계산 코드도 따로 수정해야 한다.
5. **명령 중복 처리:** update_id 저장이 없다. 작업 요청 후 접수 답장 실패 등으로 업데이트가 재전달되면 같은 작업을 다시 요청할 수 있다.
6. **동시 실행 제어 부재:** Actions concurrency 설정이 없어 수동·정기 작업이 겹치면 중복 발송과 캐시 이력 충돌 가능성이 있다.
7. **설정 변경의 비동기성:** `/stage`와 `/stop`은 별도 workflow다. 이미 진행 중인 수집에 즉시 반영되지 않으며 동시 설정 푸시는 충돌할 수 있다.
8. **다중 관리자 불일치:** Worker는 쉼표 구분 관리자 여러 명을 지원하지만 단계 변경 완료 알림은 전체 문자열을 하나의 chat ID로 사용한다. 설정 변경은 성공해도 완료 알림이 실패할 수 있다.
9. **dry run의 부수 효과:** AI 분석, 오래된 이력 정리, 결과 저장은 수행한다. `/dry` 접수 답장도 전송된다. 완전 무변경·무비용 모드는 아니다.
10. **불완전한 추적 기록:** 원문·모델 원문 응답·당시 프로필·사용 토큰을 한 실행 단위로 보존하지 않아 추천 근거 재구성이 어렵다. 캐시가 사라지면 과거 공고를 새 공고로 볼 수 있다.
11. **시간대 불일치 가능성:** 일정은 KST 환산이지만 Python은 환경의 date.today/datetime.now를 쓴다. 자정 전후 수동 실행 등에서 날짜 표시가 달라질 수 있다. 정기 시각에는 UTC와 KST 날짜가 같아 드러나지 않을 수 있다.
12. **배포 재현성 제한:** 테스트 파일·의존성 잠금 파일을 발견하지 못했다. Worker는 README상 편집기에 붙여 배포하는 방식이며 별도 배포 설정을 찾지 못했다. 저장소와 실제 배포 코드 일치 여부는 미확인이다.

## 12. 외부 소개용 문안

StartupRadar는 대학생 창업동아리와 예비창업팀을 위한 AI 기반 창업 지원정보 수집·알림 도구입니다. 정부·공공기관, 대학 창업지원단, 액셀러레이터와 재단의 정보를 모으고, 팀의 성장 단계와 관심 분야를 바탕으로 관련 공고를 선별해 텔레그램으로 전달합니다. 지원 혜택과 마감일, 적합도와 핵심 요약을 함께 제공하며, 관리자는 텔레그램에서 수집 실행과 팀 단계 변경을 요청할 수 있습니다.

Python 수집·분석 모듈, Claude API, GitHub Actions, Cloudflare Worker를 연결해 반복적인 정보 탐색 부담을 줄이는 데 초점을 맞췄습니다. 현재는 한 동아리의 공통 프로필에 맞춘 운영 형태이며 수집 범위, AI 분석 정확도, 발송 이력과 장애 감지에는 보완이 필요합니다. 지원 여부를 결정할 때 원문 공고의 조건을 최종 확인하는 방식으로 활용할 수 있습니다.
